Big-O em Sistemas Operacionais

Gerenciamento de Memória & Processos

Notação Big-O no Núcleo do Sistema Operacional

Em um Sistema Operacional, a eficiência de algoritmos de gerenciamento de memória e escalonamento de processos determina a fluidez e estabilidade de todo o sistema. A notação Big-O expressa o limite superior de tempo ou espaço que um algoritmo necessita à medida que a carga de trabalho ($n$) cresce.

O(1)

Previsibilidade Real-Time

Garante resposta em tempo constante, indispensável para interrupções de hardware e schedulers de tempo real.

O(log n)

Escala de Grande Porte

Permite gerenciar milhares de threads e blocos de memória com degradação mínima de desempenho (ex: CFS Scheduler).

O(n²)

Gargalo do Kernel

Complexidades quadráticas causam travamentos em larga escala e devem ser evitadas ou substituídas em SOs modernos.

Resumo Geral das Complexidades em SOs

Complexidade Nome Aplicação em SO Avaliação em Kernel
O(1) Constante O(1) Linux Scheduler, Freelist Allocation, Bitmap Lookups Excelente
O(log n) Logarítmico Completely Fair Scheduler (Red-Black Tree), Buddy Allocator Muito Bom

COMPLEXIDADE IDEAL

O(1) — Complexidade Constante

O tempo de execução permanece rigorosamente o mesmo, independentemente da quantidade de processos ou blocos de memória no sistema.

T(n) = c

Aplicação Real em Sistemas Operacionais

  • O(1) Linux Scheduler (Kernel 2.6): Utilizava duas matrizes de prioridade (`active` e `expired`) com bitmaps, obtendo o próximo processo via instrução assembly de bitscan (`sched_find_first_bit`).
  • Alocação por Free List (Pilha/Fila): Inserir e remover um bloco de memória do topo de uma lista encadeada de blocos livres é uma operação puramente de ponteiros.
  • Acesso a Tabelas de Páginas de Nível Único: Indexação direta em array através do número da página virtual (VPN).

Por que o O(1) Scheduler foi substituído no Linux?

Apesar da velocidade constante $O(1)$, o scheduler do Linux 2.6 usava heurísticas complexas para calcular a "interatividade" do processo. Isso gerava *starvation* (esfaimação) para certas tarefas de fundo. Por isso, foi substituído pelo CFS ($O(\log n)$), priorizando a **justiça** sobre a velocidade absoluta de constantes.

C Code — Kernel Memory Free List O(1) Allocation 
typedef struct Block {
    size_t size;
    struct Block* next;
} Block;

Block* free_list_head = NULL;

// Desalocação O(1): Insere no topo da lista
void kfree_fast(Block* block) {
    block->next = free_list_head;
    free_list_head = block; 
}

// Alocação O(1): Remove do topo da lista
Block* kmalloc_fast() {
    if (!free_list_head) return NULL;
    Block* allocated = free_list_head;
    free_list_head = free_list_head->next;
    return allocated;
}
Instruções executadas: ~3 instruções Tempo de resposta: Constante
ALTAMENTE ESCALÁVEL

O(log n) — Complexidade Logarítmica

A cada passo do algoritmo, o espaço de busca é reduzido pela metade. Excelente para gerenciar milhares de recursos simultâneos.

T(n) = \log_2(n)

Uso no Kernel Linux e SOs Modernos

  • CFS (Completely Fair Scheduler): Utiliza uma Árvore Red-Black (`struct rb_root`) ordenada pelo tempo de execução virtual (`vruntime`). A escolha da próxima tarefa a executar leva tempo $O(1)$ (nó mais à esquerda), mas a inserção/remoção da árvore custa $O(\log n)$.
  • Buddy Allocator (Gerenciamento de Memória Física): Divide a memória em blocos de potências de 2 ($2^k$). A busca por blocos "irmãos" (buddies) e fusão/divisão exige $O(\log n)$ onde $n$ é o número de ordens de memória.

Impacto na Prática

Mesmo se o sistema operacional tiver **1.000.000 de tarefas** rodando, o CFS realiza no máximo cerca de **20 comparações** na árvore Red-Black para inserir ou reordenar uma tarefa!

C Code — Red-Black Tree Insertion (CFS) O(log n) Insertion 
void enqueue_task_cfs(struct rq *rq, struct task_struct *p) {
    struct rb_node **link = &rq->cfs.tasks_timeline.rb_node;
    struct rb_node *parent = NULL;
    u64 vruntime = p->se.vruntime;

    // Busca logarítmica O(log n) na árvore
    while (*link) {
        parent = *link;
        struct sched_entity *entry = rb_entry(parent, ...);
        if (vruntime < entry->vruntime)
            link = &parent->rb_left;
        else
            link = &parent->rb_right;
    }
    // Inserção e Rebalanceamento O(log n)
    rb_link_node(&p->se.run_node, parent, link);
    rb_insert_color(&p->se.run_node, &rq->cfs.tasks_timeline);
}
Para n = 1.000.000: ~20 operações Estabilidade: Extrema
CUIDADO EM LARGA ESCALA

O(n) — Complexidade Linear

O tempo cresce de forma diretamente proporcional ao número de elementos. Pode causar gargalos se $n$ for elevado.

T(n) = c \cdot n

Ocorrências em Gerenciamento de Memória / SO

  • Algoritmos de Alocação de Memória (Best-Fit / First-Fit em Lista Ligada): Percorrem toda a lista de blocos livres para encontrar o bloco mais adequado.
  • Garbage Collection (Mark-and-Sweep): A fase de varredura (*sweep*) examina todos os objetos alocados na heap em tempo $O(n)$.
  • Substituição de Páginas (Clock Algorithm / FIFO): No pior caso, varre todos os quadros de memória física para encontrar uma página para substituição.

Estratégia de Melhoria

Para otimizar um Best-Fit de $O(n)$, os SOs modernos convertem a lista ligada simples em uma **Árvore AVL / Red-Black** ou usam um **Segregated Free List** (listas separadas por tamanho fixo), reduzindo o custo de alocação para $O(\log n)$ ou até $O(1)$.

C Code — Memory Allocation Best-Fit O(n) Linear Scan 
// Procura o menor bloco suficiente percorrendo a lista toda
Block* best_fit_alloc(size_t requested_size) {
    Block* curr = free_list_head;
    Block* best = NULL;

    while (curr != NULL) { // O(n) chamadas
        if (curr->free && curr->size >= requested_size) {
            if (best == NULL || curr->size < best->size) {
                best = curr;
            }
        }
        curr = curr->next;
    }
    return best; // Retorna o melhor bloco encontrado
}
Para 10.000 blocos: 10.000it Risco: Aumento de latência
ORDENAÇÃO EFICIENTE

O(n log n) — Complexidade Log-Linear

Complexidade típica dos melhores algoritmos de ordenação por comparação (QuickSort, MergeSort, HeapSort).

T(n) = n \cdot \log_2(n)

Uso em Kernels e Utilitários de SO

  • Reorganização Periódica de Tabelas de Processos/Páginas: Ordenar processos para relatórios de diagnóstico (`ps`, `top`) ou auditoria de recursos.
  • Sort do Kernel Linux (`lib/sort.c`): O Kernel implementa HeapSort $O(n \log n)$ com garantia de tempo no pior caso e sem depender de recursão profunda no stack do kernel.
  • Consolidação de Memória / Defragmentação Batch: Ordenar endereços de blocos livres para fusão em lote (*coalescing*).

Por que não usar QuickSort puro no Kernel?

O QuickSort possui pior caso de $O(n^2)$ e consumo de pilha recursiva. Para evitar o estouro de pilha (*kernel stack overflow*), o Linux prefere **HeapSort** ou **Introsort**, mantendo a garantia estrita de $O(n \log n)$.

C Code — Linux Kernel HeapSort O(n log n) Guaranteed 
// Implementação baseada no lib/sort.c do Kernel Linux
void sort(void *base, size_t num, size_t size,
          int (*cmp_func)(const void *, const void *)) {
    // 1. Constrói o Max Heap: O(n)
    for (int i = num / 2 - 1; i >= 0; i--)
        sift_down(base, i, num, size, cmp_func);

    // 2. Extrai elementos um a um: O(n log n)
    for (int i = num - 1; i > 0; i--) {
        swap(base, base + i * size, size);
        sift_down(base, 0, i, size, cmp_func);
    }
}
Garantia de Espaço: O(1) in-place Pior Caso: O(n log n)
INVIÁVEL EM ESCALA

O(n²) — Complexidade Quadrática

O tempo de execução dobra ao quadrado conforme a entrada cresce. Pode colapsar a performance do sistema operacional.

T(n) = c \cdot n^2

Onde surge em Teoria de SOs?

  • Algoritmo do Banqueiro (Banker's Algorithm - Dijkstra): Usado para prevenção e detecção de Deadlocks. No pior caso, possui complexidade de tempo $O(m \cdot n^2)$, onde $n$ é o número de processos e $m$ o de recursos.
  • Escalonadores Primitivos / Legados: Matrizes de dependência sem índices ou escalonadores baseados em BubbleSort de filas de prioridades.

Por que o Algoritmo do Banqueiro NÃO é usado no Linux/Windows?

Devido ao custo $O(m \cdot n^2)$ e à necessidade de saber os recursos máximos exigidos antecipadamente por cada processo, SOs de propósito geral usam a **Estratégia do Avestruz** (ignorar deadlocks e tratá-los no espaço do usuário se ocorrerem) em vez de validar cada requisição com $O(n^2)$.

C Code — Banker's Safety Algorithm O(n²) Complexity 
// Verificação de Segurança de Deadlock O(n²)
bool is_safe_state(int P, int R, int alloc[P][R], int need[P][R], int avail[R]) {
    bool finish[P]; memset(finish, 0, sizeof(finish));
    int count = 0;

    while (count < P) {
        bool found = false;
        for (int p = 0; p < P; p++) { // Loop 1: n
            if (!finish[p]) {
                int r;
                for (r = 0; r < R; r++) // Loop 2: m
                    if (need[p][r] > avail[r]) break;
                if (r == R) { // Encontrou processo seguro
                    for (int k = 0; k < R; k++) avail[k] += alloc[p][k];
                    finish[p] = true; found = true; count++;
                }
            }
        }
        if (!found) return false; // Deadlock detectado
    }
    return true;
}
Para 10.000 processos: 100.000.000 ops! Resultado: System Freezing

Estratégias de Otimização no Kernel

Engenheiros de Sistemas Operacionais utilizam padronizações de estruturas de dados e técnicas avançadas para refatorar algoritmos de classes desfavoráveis ($O(n^2)$ ou $O(n)$) para ordens de grandeza muito superiores ($O(\log n)$ ou $O(1)$).

1. Transição de $O(n)$ para $O(1)$: Bitmaps + Instruções de Hardware

DE: O(n) PARA: O(1)

**Problema:** Iterar em uma lista encadeada procurando por uma página de memória livre custa $O(n)$.
**Solução do SO:** Mapear os blocos de memória em um **Bitmap** e utilizar instruções da CPU como `__builtin_clz` (Count Leading Zeros) ou `bsf` (Bit Scan Forward). A CPU encontra o primeiro bit livre em **1 único ciclo de clock**, atingindo $O(1)$ real.

2. Transição de $O(n)$ para $O(\log n)$: Substituição de Lista por Árvores Red-Black

DE: O(n) PARA: O(log n)

**Problema:** O escalonador O(n) antigo do Linux varria uma lista encadeada de tarefas para decidir quem rodava a seguir. Se o sistema tivesse 10.000 tarefas, o tempo do scheduler era um gargalo.
**Solução do SO:** Migração para o CFS com Árvores Red-Black. O acesso a menor tarefa (`rb_leftmost`) é mantido em ponteiro $O(1)$ e re-inserções duram $O(\log n)$.

3. Transição de $O(n^2)$ para $O(n \log n)$ ou Evitação Total em Deadlock

DE: O(n²) PARA: O(n log n) / Ignorado

**Problema:** O Algoritmo do Banqueiro tem complexidade $O(m \cdot n^2)$ para garantir prevenção absoluta contra deadlocks.
**Solução do SO:** Sistemas modernos substituem a verificação contínua do Banqueiro por **Hierarquia de Travas (Lock Ordering)** com detecção baseada em Grafo de Alocação de Recursos (RAG) verificada apenas periodicamente ou em threads em background.
